## 2026-10-14 · E1 运动候选在 MoCA 上的单帧召回

- 命令：`uv run python scripts/eval_candidates.py --workers 6`（640 宽，141 段）
- 剔除复制帧 618 个（判据 `DUP_FRAC = 0.005`），评测 36,491 帧（插值真值）

| 运动标签 | 帧数 | 命中 | IoU≥0.3 | 每帧误报 | 无候选帧 |
|---|---|---|---|---|---|
| locomotion（移动） | 21,739 | 68.6% | 34.9% | 1.31 | 24.4% |
| subtle_motion（轻微动作） | 11,633 | 29.0% | 4.3% | 0.33 | 63.9% |
| still（静止） | 3,040 | 1.5% | 0.2% | 0.32 | 89.4% |
| 全部 | 36,491 | 50.2% | 22.2% | 0.91 | — |

- 每段视频命中率：平均 57.6%，四分位 21.6% / 69.7% / 92.2%（双峰：一部分视频几乎全中，一部分几乎全不中）
- 耗时：19.5ms/帧（6 进程并行时的单帧耗时，含争用）

解读：

- 这是**单帧**召回，没有时间累积；下游跟踪器（Kalman 预测 + 断档缝合）与「目标不动时跟随背景等待」的机制会弥补一部分缺口，须看端到端指标（E2）。
- 静止帧召回接近 0 符合预期：不动就没有运动信号，这正是选择器「等待」机制的用途。
- IoU 远低于「命中」：候选框只框住目标的运动部分（例如只框到在动的腿），框的范围不准，但中心多数落在目标上。
- ⚠️ 按运动标签分组依赖「稀疏标签沿用」的推断（见 `datasets.moca.Sequence.motion`）。

## 2026-10-14 · E2 端到端跟拍（虚拟取景窗）

- 脚本：`vision/scripts/eval_e2.py`；命令：`uv run python scripts/eval_e2.py --workers 6 [--frac 0.33]`
- 结果：`runs/e2-frac0.5-20261014-103010.json`、`runs/e2-frac0.33-20261014-102453.json`（同一配置重跑两次，数字逐位相同）
- 数据：141 段，剔除复制帧 618 个，保留真实时间戳（`k / 24` 秒，帧间隔因此不均匀）；评测 36,632 个有真值的帧
  （比 E1 多 141 帧：E1 跳过每段第 0 帧，这里不跳 —— 第 0 帧取景窗在画面中心，也算进时间占比）
- 核心代码**未改**：`core.run` 原样接受外部候选（`mot.Detection` 格式）与外部 `shifts`；时钟传真实时间戳
  `timing.Clock(n, ts, roi_w=640)`（不传会按 30Hz 均匀假设）。

### 设置

```text
全幅 640 宽 ─▶ MotionCandidates(640) ─▶ 候选 + bg_shift ─▶ core.run(gate, shifts) ─▶ 瞄准点 ─▶ 取景窗中心
```

- **取景窗**：宽高 = 全幅 × `frac`（默认 0.5，与宿主 `WINDOW_FRAC` 一致），钳在画面内，几何与
  `src-tauri/src/gimbal.rs` 一致；初始在画面中心；瞄准点为空时不动。
- **开环**（`core` / `core_speed` / `naive`）：感知看全幅，瞄准结果只决定取景窗放在哪；第 k 帧的取景窗
  由第 k 帧的瞄准点决定（零延迟）。⚠️ 真实云台看不到取景窗外的画面，开环结果不能当作系统效果。
- **闭环**（`closed` / `closed_speed` / `closed_naive`）：每帧从全幅裁出当前取景窗交给候选生成（相当于
  装在云台上的相机，取景窗的移动被单应估计当作相机运动吸收），瞄准点从取景窗坐标换回全幅后决定**下一帧**
  的取景窗；评测用这一帧实际裁出的取景窗（含一帧延迟）。候选阈值按全幅 640 宽缩放（像素密度不变）。
- **在线执行**：`causal` 与 `closed*` 逐帧调用 `Tracker.step` / `Selector.step` / `Aim.step`，断档回填只用到
  当前帧为止的观测。`core`（离线 `core.run`）与 `causal` 在全部 36,632 帧上瞄准点**逐帧相同**：`fill_gaps`
  回填出的未来点只落在「当前帧没有观测」的轨迹上，而选择器只考虑当前帧有观测的轨迹 ⇒ `core.run` 的回填
  实际上不前视。剩下的前视只有时钟的中位帧间隔（用整段时间戳算）。
- **对照组**：(a) `center` 取景窗固定在画面中心；(b) `naive` 每帧对准「运动量最大」的候选（先比 conf =
  残余速度中位数（封顶 1.0），并列比面积），无候选不动，不用跟踪器 / 选择器 / 控制器；(c) `core_speed`
  消融 `gate="speed"`。
- **指标**：time-in-frame = 真值框中心在取景窗内的帧占比（主指标）；完全在窗内的帧占比；窗中心到真值中心
  距离 ÷ 窗对角线；首次锁定 = 从首个有真值的帧起，到真值中心**连续 0.5 秒**在窗内的起点所经过的秒数。

### 解读

- ⛔ **主结论是负面的**：在 MoCA 上，固定在画面中心的取景窗（90.9%）高于系统的所有变体（开环 78.4%、
  闭环 81.4%）和朴素对准（79.8% / 84.2%）；`frac = 0.33` 时差距更大（70.1% 对 49.9% / 38.9%）。逐段
  配对也是固定中心占优的段数多。
- 固定中心这么强，说明 MoCA 的拍摄者本身在用手持相机跟拍目标 ⇒ 目标大多已在画面中央。这个数据集上
  「中心先验」就是一个很强的跟拍器，取景窗的任何主动移动都要先超过它。⚠️ 这意味着 MoCA 只能衡量
  「主动跟拍会不会把已经居中的目标弄丢」，不能衡量「能不能把偏离中心的目标找回来」。
- **时间连续性补回了多少**：在 E1 单帧未命中的帧上，`core` 的 in-frame 是 80.6%，`naive` 是 72.8% ——
  跟踪 / 等待机制在没有运动信号的帧上比「无候选就不动」高 7.8 个百分点；但在 E1 命中的帧上 `core`
  （76.2%）反而低于 `naive`（86.8%），选择器在有正确候选时没有选中或没有跟上它。两者相抵，开环全体
  `core` 与 `naive` 接近（78.4 对 79.8）。同样的帧上 `center` 两类都在 88% 以上，所以「补回」是相对朴素
  方法而言，不是相对中心先验。
- **按运动标签**：still 帧上系统（82.6%）明显高于朴素（57.8%）—— 目标不动时朴素方法会被其他运动带走，
  等待机制在这里起作用；locomotion 帧上系统（74.2%）低于朴素（81.9%）。
- **门控消融**：开环下 `speed` 门控高于 `uncertainty`（81.2 对 78.4，subtle_motion 上 91.0 对 85.6）；闭环下
  两者持平（81.2 对 81.4）。MoCA 是 24fps 去复制帧后的不均匀间隔，合成场景上 uncertainty 的优势（低帧率）
  在这里没有体现出来，反而略差。
- **首次锁定**：所有方法的中位数都是 0 秒 —— 目标在第一帧就在中心窗里，这个指标在 MoCA 上几乎没有区分力。

### 局限

- 开环高估真实效果（感知看全幅、零延迟）；闭环更接近云台，但取景窗是全幅里的数字裁剪，没有真实云台的
  机械延迟与运动模糊。`frac = 0.5` 时闭环反而高于开环，`frac = 0.33` 时闭环远低于开环 —— 两种回路的
  相对关系随取景窗大小翻转。
- 闭环下取景窗内单应估计失败 35 帧（`frac = 0.33` 时 148 帧），失败帧按零背景位移处理；开环全幅 0 帧失败。
  `closed_naive` 不用背景位移，失败次数未统计。
- 背景位移取单应矩阵把画面中心映到哪，抽查 arabian_horn_viper：与逐帧相位相关累加的平移在前 120 帧
  方向一致，之后分歧变大（第 330 帧时累计 y 方向 2,300px 对 1,193px）。哪个更接近真实未核实。
- 按运动标签分组依赖「稀疏标签沿用」的推断（同 E1）。
- 参数全部是前期系统的初值（`core.timing` 注释已说明须在本项目数据上重新标定），E2 没有调参。
- 每段只跑一次（流程是确定性的，重跑结果逐位相同），没有随机性带来的方差可报。

### 修复 1：观测噪声 R 按实测标定（只用 dev）

结果：`runs/calib-r-dev-20261020-033625.json`。样本 = dev 每帧与真值框匹配的运动候选（E1 判据：中心在框内、
面积 ≤ 4 × 真值面积），残差 `e = 候选中心 − 真值中心`（640 宽像素）。三种口径：

| 口径 | 样本 | σx, σy（px） | 说明 |
|---|---|---|---|
| **帧间差** `Δe = e[k] − e[k−1]`，`σ² = (1.4826·MAD(Δe))² / 2` | 2,556 对（61 段；相邻两帧都恰好一个匹配） | **3.9, 4.1** | 真值扣掉目标运动，差分扣掉持续偏置 |
| 静态残差，每段去中位数，`σ = 1.4826·MAD` | 4,888（64 段；只用人工标注帧） | 66.9, 48.3 | 含「点云落在身体哪一块」的持续偏置 |
| 静态残差，不去偏 | 4,888 | 73.3, 54.4 | |

**取帧间差口径**，`R = diag(15.2, 16.7)`（`mot.MEAS_VAR`）。理由：Kalman 的 R 描述逐帧独立的观测噪声；
静态残差主要是候选落在目标哪一部分的偏置（按真值框大小分三组，σx 从 31 涨到 80、126 px，与框大小成比例），
它在一条轨迹的寿命里近似不变、由状态吸收，不是白噪声。没有在 R 网格里按 E2 分数挑值（10-14 的 R 扫描
曾显示 R≈80 时全集 81.9%，该值未被采用）。
⚠️ 帧间差是重尾的：|Δe| 中位 7.1px，但 95% / 99% 分位 55 / 151px（候选在身体部位间跳变）；按方差而非
MAD 估计会得到 σ² ≈ 392 / 194。MAD 口径的 R 只描述主峰，长尾不由 R 吸收 —— 这可能是此修复单独打开时
没有收益的原因之一（见下表）。「恰好一个匹配」的样本偏向小目标、干净的帧。

### 修复 2：印证中的远跳位置 `chal` 每帧随背景平移

原代码只在远跳分支里 `chal += bg`，中间隔着没有候选的帧时 `chal` 停在旧画面坐标上。改为与 `pos += bg`
同处每帧平移（`Selector(shift_chal=False)` 复现旧行为，只用于消融）。单元测试
`tests/test_fixes.py::test_the_challenger_moves_with_the_background_every_frame`。

### E2b 协议：背景稳定化（`--protocol e2b`）

- **画布**：`gimbal_vision.stabilize`，相邻帧 SIFT（1500 点）+ 比值检验 0.75 + RANSAC 单应（3px），取画面中心
  的平移累积成偏移 `o[k]`（画布 = 画面 + `o[k]`）。与被测方法（Shi-Tomasi + LK + RANSAC）用不同的特征与匹配，
  不看真值、不看任何方法的输出，所有方法共用同一份 `o[k]`（缓存 `runs/diag_cache/stab-*.pkl`）。
  内点 < 15 记 0 平移：dev 260 帧（1.2%）、test 190 帧（1.2%）。
- **取景窗住在画布上**：瞄准点为 `None` 时在画布（世界）里不动；有瞄准点时中心 = 瞄准点 + `o[k]`。唯一约束：
  **取景窗中心钳在当帧素材范围内**（中心像素必须真实拍到），窗的其余部分可以伸出素材、补黑。比 E2 的
  「整窗钳在画面内」宽松 —— 后者在摄影师跟拍时会把窗往目标所在的画面中心推。
- **固定点基线**：画布上的初始画面中心，同样受上面的钳位。⚠️ 钳位仍然泄漏一部分跟拍信息：素材摇出去时
  窗被素材边界拖着走（固定点在 dev 14.7%、test 16.9% 的帧上被钳）。
- **开环**：感知看原始素材全幅（与 E2 同一份候选、同一组瞄准点），只是取景窗的摆放换成上面的规则 ⇒
  E2 与 E2b 的开环差别只来自「首次估计之前窗在哪里」和钳位规则。
- **闭环**：每帧按窗在当帧素材中的位置裁剪，伸出素材的部分补黑；候选生成的角点只取有效区（腐蚀 12px），
  跟到下一帧落在无效区的点丢掉（`MotionCandidates(..., mask)`，测试
  `test_a_moving_black_border_is_not_motion_when_masked`）。
- **漂移**：不做分段重置 —— 重置时把窗放回画面中心等于每段重新给一次跟拍 oracle。累积误差只影响「画布上
  的固定点」对应世界里哪一点（即固定点基线）；开环方法的窗由画面坐标的瞄准点决定，不受累积误差影响。
  自检（`runs/diag-e2b-stab-dev-20261020-041144.json`、`runs/diag-e2b-stab-test-20261020-042240.json`）：
  2 秒（48 帧）区间内逐帧累积对比直接长基线配准（只用累积位移 < 0.5 倍画面宽、内点 ≥ 30 的区间），
  误差中位 / 90% / 99% 分位 dev 1.2 / 12.8 / 224.5 px（614 个区间）、test 1.5 / 15.3 / 96.2 px（426 个）；
  dev 上 > 50px 的 22 个区间集中在 7 段（black_cat_1、flounder_6、chameleon、lion_cub_0 等）。与被测方法自己的
  LK 背景位移逐帧差中位 0.03px、99% 分位 3.3px（test 10.5px）；整段累积终点之差 ÷ 路程的中位数 3.2%（test 3.4%），
  black_cat_1 为 25%（有台标）。
- **目标确实离开了初始中心**：真值中心在画布上到初始中心的距离 ÷ 取景窗对角线，`frac = 0.5` 下四分位

### 局限

- E2b 的画布只建模平移；变焦、旋转、视差会变成漂移。长基线自检的 99% 分位达到百 px 量级，集中在少数段；
  这些段上「画布固定点」不对应世界里的固定点，主要影响固定点基线。
- 中心钳位仍向所有方法（尤其固定点）泄漏一部分跟拍信息；完全不钳则窗可以整个落在没拍到的区域，闭环
  无从感知。
- 闭环补黑：窗伸出素材时可用像素变少。真实云台没有「素材边界」，这是用跟拍素材模拟固定机位带来的伪影。
- R 的 MAD 标定只描述残差主峰；重尾部分（部位跳变）没有建模。
- dev / test 各约 70 段，按运动标签分组时 still 只有 1.3–1.8k 帧（以 still 为主的视频 dev 4 段 / test 3 段），
  still 列的波动很大。

### 设定（跑 dev 之前定好，之后未改）

在**原始 24 Hz 帧号**上按间隔串 `g_1, g_2, …` 取目标帧 `k_j = k_{j−1} + g_j`（`k_0 = 0`）；目标帧是复制帧时在
`±⌊g_j/2⌋` 帧内取最近的非复制帧（等距取较早的，必须晚于上一保留帧），找不到则该采样点丢失。保留帧用真实
时间戳 `k/24`，真值按保留帧评测；E2b 画布偏移在完整 24 Hz 序列上算好再取保留帧（尺子不随帧率变）。

|---|---|---|---|---|---|

| j3 重 | {1,5}，概率 {.75,.25}（多数帧 24 Hz 到达，1/4 的间隔是 5 帧卡顿） | 12 | 24 / 24 | 5.0 | 0.86 |

### 解读

- ⛔ **合成场景里速度门在低帧率下崩溃（表 4-4：15 Hz 命中 7%）在 MoCA 上没有出现。** 开环下两种门控在 24 → 6 Hz、
  三档抖动下的差都在 3 个百分点以内，高下随条件、协议、取景窗变；闭环下速度门多数格更高。与「不确定性门控在
  低帧率更稳」的预期不符。
- **原因在场景，不在门宽**：速度门的半径确实按 `GATE_PPS·dt` 线性变宽（112 → 450 px），误关联次数也随之增加（24 Hz
  5.6 次 / 分钟 → 12 Hz 10.9 次），但 MoCA 的运动候选稀疏：只有 11–17% 的帧在目标之外还有别的候选，且中位距离约
  250 px，40 px 内从未出现。合成场景的失效机制（漏检一帧时轨迹改配到相邻物体）需要「门宽 > 物体间距」，在 MoCA 上
  只在 ≤ 11% 的帧上满足，所以宽门的代价很小。
- **不确定性门的主要问题是太窄**：在所有条件下都有 44–51% 的框内目标候选被马氏门拒掉，NIS 中位 6–9.5（自洽时服从
  χ²(2)，中位约 1.4），目标轨迹续上的比例 38–46%，速度门是 63–74%；轨迹出生率与目标身份切换约为速度门的 1.7–3 倍。
  这与 6.6 节的结论一致（候选在身体部位之间跳变的重尾残差不由 R 吸收）。帧率降低时过程噪声按 `dt` 增长，门变宽
  （27 → 57 px）、NIS 降低（9.1 → 6.1）、拒绝率降低（49.9 → 43.7%）—— 不确定性模型在低帧率下反而更自洽，这与 6 Hz
  开环下它略占优（test 四个设置 +1.1 ~ +2.8，dev 为 +2.1 / −0.3 / +0.4 / −0.1）方向一致，但幅度小、未显著。
- **抖动**（同 12 Hz 平均帧率）：开环 core 相对 r12 下降 0–6.8 个百分点（两种门控都是；0.33 窗更明显，j2 / j3 的下降大于 j1）；两种门控对抖动的敏感度
  没有一致差别。j2 / j3 的中位间隔是 1 个原始帧，`Clock.hz()` 报 24 Hz（实际平均 12 Hz）：按中位间隔换算的帧数类量
  （`frames_in`：MISS_SEC、FILL_SEC、CONFIRM 帧数等）会按 24 Hz 换算，这是系统在强抖动下的实际行为。
- **帧率对开环系统影响很小，甚至略升**（test E2b 0.5 core fixed：72.4 → 75.2 → 76.2 → 79.0；dev 69.3 → 69.6 → 73.5 → 70.9）；固定点不随帧率变（61.1–62.0），说明不是
  抽帧改变了评测帧分布。原因未查清，可能与按帧计的残留量有关（如净位移要求窗口首个观测不晚于起点后 2 帧，帧率低时
  2 帧对应更长时间），未验证。**闭环随帧率明显下降**（E2b 0.5 closed fixed 62.3 → 52.8，closed_naive 77.0 → 69.4）：
  闭环有一帧延迟，帧率低时延迟按 1/f 增大，且目标在一帧里走得更远、更容易出窗。
- **对 HZ_MIN 的含义**：开环在 6 Hz 不比 24 Hz 差，`HZ_MIN = 12` 对开环过于保守；闭环在 6–8 Hz 的 E2b 0.5 下
  （52.8–55.2）低于固定点（61.8–62.0），若护栏接入、低于阈值时不动，闭环这一格会更好。12 Hz 边界上的浮点问题须在
  接入前处理（例如阈值比较留容差）。

### 局限

- 降采样是从 24 Hz 素材里抽帧，不是低帧率相机：曝光时间（运动模糊）不随帧率变；源帧率低于 24 Hz 的视频去复制帧后
  本来就有不均匀间隔。
- 抖动只模拟「帧到达时刻」的分布，时间戳本身准确；真实链路里的时间戳误差没有模拟。
- 每个条件每段只有一种随机实现（固定种子），没有对种子做方差估计；dev / test 各约 70 段，格间差值未做显著性检验
  （只对 6 Hz 的逐段胜负做了符号检验）。
- 「误关联」「续上」以真值框（及扩大一倍的框）判定；候选只框住身体运动部位时，可能把正确关联判成 ring / steal。
