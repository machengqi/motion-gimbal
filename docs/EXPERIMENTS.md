## 2026-10-14 · E1 运动候选在 MoCA 上的单帧召回

- 命令：`uv run python scripts/eval_candidates.py --workers 6`（640 宽，141 段）
- 剔除复制帧 618 个（判据 `DUP_FRAC = 0.005`），评测 36,491 帧（插值真值）

| 运动标签 | 帧数 | 命中 | IoU≥0.3 | 每帧误报 | 无候选帧 |
|---|---|---|---|---|---|
| locomotion（移动） | 21,739 | 68.6% | 34.9% | 1.31 | 24.4% |
| subtle_motion（轻微动作） | 11,633 | 29.0% | 4.3% | 0.33 | 63.9% |
| still（静止） | 3,040 | 1.5% | 0.2% | 0.32 | 89.4% |
| 全部 | 36,491 | 50.2% | 22.2% | 0.91 | — |

- 每段视频命中率：平均 57.6%，四分位 21.6% / 69.7% / 92.2%（双峰：一部分视频几乎全中，一部分几乎全不中）
- 耗时：19.5ms/帧（6 进程并行时的单帧耗时，含争用）

解读：

- 这是**单帧**召回，没有时间累积；下游跟踪器（Kalman 预测 + 断档缝合）与「目标不动时跟随背景等待」的机制会弥补一部分缺口，须看端到端指标（E2）。
- 静止帧召回接近 0 符合预期：不动就没有运动信号，这正是选择器「等待」机制的用途。
- IoU 远低于「命中」：候选框只框住目标的运动部分（例如只框到在动的腿），框的范围不准，但中心多数落在目标上。
- ⚠️ 按运动标签分组依赖「稀疏标签沿用」的推断（见 `datasets.moca.Sequence.motion`）。

## 2026-10-14 · E2 端到端跟拍（虚拟取景窗）

- 脚本：`vision/scripts/eval_e2.py`；命令：`uv run python scripts/eval_e2.py --workers 6 [--frac 0.33]`
- 结果：`runs/e2-frac0.5-20261014-103010.json`、`runs/e2-frac0.33-20261014-102453.json`（同一配置重跑两次，数字逐位相同）
- 数据：141 段，剔除复制帧 618 个，保留真实时间戳（`k / 24` 秒，帧间隔因此不均匀）；评测 36,632 个有真值的帧
  （比 E1 多 141 帧：E1 跳过每段第 0 帧，这里不跳 —— 第 0 帧取景窗在画面中心，也算进时间占比）
- 核心代码**未改**：`core.run` 原样接受外部候选（`mot.Detection` 格式）与外部 `shifts`；时钟传真实时间戳
  `timing.Clock(n, ts, roi_w=640)`（不传会按 30Hz 均匀假设）。

### 设置

```text
全幅 640 宽 ─▶ MotionCandidates(640) ─▶ 候选 + bg_shift ─▶ core.run(gate, shifts) ─▶ 瞄准点 ─▶ 取景窗中心
```

- **取景窗**：宽高 = 全幅 × `frac`（默认 0.5，与宿主 `WINDOW_FRAC` 一致），钳在画面内，几何与
  `src-tauri/src/gimbal.rs` 一致；初始在画面中心；瞄准点为空时不动。
- **开环**（`core` / `core_speed` / `naive`）：感知看全幅，瞄准结果只决定取景窗放在哪；第 k 帧的取景窗
  由第 k 帧的瞄准点决定（零延迟）。⚠️ 真实云台看不到取景窗外的画面，开环结果不能当作系统效果。
- **闭环**（`closed` / `closed_speed` / `closed_naive`）：每帧从全幅裁出当前取景窗交给候选生成（相当于
  装在云台上的相机，取景窗的移动被单应估计当作相机运动吸收），瞄准点从取景窗坐标换回全幅后决定**下一帧**
  的取景窗；评测用这一帧实际裁出的取景窗（含一帧延迟）。候选阈值按全幅 640 宽缩放（像素密度不变）。
- **在线执行**：`causal` 与 `closed*` 逐帧调用 `Tracker.step` / `Selector.step` / `Aim.step`，断档回填只用到
  当前帧为止的观测。`core`（离线 `core.run`）与 `causal` 在全部 36,632 帧上瞄准点**逐帧相同**：`fill_gaps`
  回填出的未来点只落在「当前帧没有观测」的轨迹上，而选择器只考虑当前帧有观测的轨迹 ⇒ `core.run` 的回填
  实际上不前视。剩下的前视只有时钟的中位帧间隔（用整段时间戳算）。
- **对照组**：(a) `center` 取景窗固定在画面中心；(b) `naive` 每帧对准「运动量最大」的候选（先比 conf =
  残余速度中位数（封顶 1.0），并列比面积），无候选不动，不用跟踪器 / 选择器 / 控制器；(c) `core_speed`
  消融 `gate="speed"`。
- **指标**：time-in-frame = 真值框中心在取景窗内的帧占比（主指标）；完全在窗内的帧占比；窗中心到真值中心
  距离 ÷ 窗对角线；首次锁定 = 从首个有真值的帧起，到真值中心**连续 0.5 秒**在窗内的起点所经过的秒数。

### 解读

- ⛔ **主结论是负面的**：在 MoCA 上，固定在画面中心的取景窗（90.9%）高于系统的所有变体（开环 78.4%、
  闭环 81.4%）和朴素对准（79.8% / 84.2%）；`frac = 0.33` 时差距更大（70.1% 对 49.9% / 38.9%）。逐段
  配对也是固定中心占优的段数多。
- 固定中心这么强，说明 MoCA 的拍摄者本身在用手持相机跟拍目标 ⇒ 目标大多已在画面中央。这个数据集上
  「中心先验」就是一个很强的跟拍器，取景窗的任何主动移动都要先超过它。⚠️ 这意味着 MoCA 只能衡量
  「主动跟拍会不会把已经居中的目标弄丢」，不能衡量「能不能把偏离中心的目标找回来」。
- **时间连续性补回了多少**：在 E1 单帧未命中的帧上，`core` 的 in-frame 是 80.6%，`naive` 是 72.8% ——
  跟踪 / 等待机制在没有运动信号的帧上比「无候选就不动」高 7.8 个百分点；但在 E1 命中的帧上 `core`
  （76.2%）反而低于 `naive`（86.8%），选择器在有正确候选时没有选中或没有跟上它。两者相抵，开环全体
  `core` 与 `naive` 接近（78.4 对 79.8）。同样的帧上 `center` 两类都在 88% 以上，所以「补回」是相对朴素
  方法而言，不是相对中心先验。
- **按运动标签**：still 帧上系统（82.6%）明显高于朴素（57.8%）—— 目标不动时朴素方法会被其他运动带走，
  等待机制在这里起作用；locomotion 帧上系统（74.2%）低于朴素（81.9%）。
- **门控消融**：开环下 `speed` 门控高于 `uncertainty`（81.2 对 78.4，subtle_motion 上 91.0 对 85.6）；闭环下
  两者持平（81.2 对 81.4）。MoCA 是 24fps 去复制帧后的不均匀间隔，合成场景上 uncertainty 的优势（低帧率）
  在这里没有体现出来，反而略差。
- **首次锁定**：所有方法的中位数都是 0 秒 —— 目标在第一帧就在中心窗里，这个指标在 MoCA 上几乎没有区分力。

### 局限

- 开环高估真实效果（感知看全幅、零延迟）；闭环更接近云台，但取景窗是全幅里的数字裁剪，没有真实云台的
  机械延迟与运动模糊。`frac = 0.5` 时闭环反而高于开环，`frac = 0.33` 时闭环远低于开环 —— 两种回路的
  相对关系随取景窗大小翻转。
- 闭环下取景窗内单应估计失败 35 帧（`frac = 0.33` 时 148 帧），失败帧按零背景位移处理；开环全幅 0 帧失败。
  `closed_naive` 不用背景位移，失败次数未统计。
- 背景位移取单应矩阵把画面中心映到哪，抽查 arabian_horn_viper：与逐帧相位相关累加的平移在前 120 帧
  方向一致，之后分歧变大（第 330 帧时累计 y 方向 2,300px 对 1,193px）。哪个更接近真实未核实。
- 按运动标签分组依赖「稀疏标签沿用」的推断（同 E1）。
- 参数全部是前期系统的初值（`core.timing` 注释已说明须在本项目数据上重新标定），E2 没有调参。
- 每段只跑一次（流程是确定性的，重跑结果逐位相同），没有随机性带来的方差可报。
